# 执行与交付链路复核（2026-11-18）

用户在 ZCode 两条旧工作待核对恢复后，要求检查链路是否还有同类问题。本轮核对 ZCode ACP → Dock 原执行回执 → Matrix 执行宿主 → Hutian 聊天/定时协调 → Web 状态和原文件入口，重点是结束与交付的区分、原运行身份、恢复与排队。

## 已修复

1. **执行已结束但无法交付时无限重试。** 原宿主对没有最终正文或超过聊天长度限制的结果抛错，后台会持续核对。现在保存单独的交付失败原因，结束该交付尝试；原生完成回执保持原样。输出长度限制、轮次限制、模型拒绝、详细结果已过期分别说明原因，不将过程文本替代最终回答。用户仍可显式核对原运行。
2. **原宿主记录缺失时误进新建执行。** 聊天已绑定 runId 而宿主暂时没有记录时，只返回待核对，禁止调用新建入口；现存回执的恢复也只使用原运行。聊天与定时的该边界现在一致。
3. **先采用结果、后校验身份。** 聊天先核对原 runId，再接纳 replied/failed/cancelled；宿主读取回执同时校验 Provider 和结果中的运行标识，实时执行桥也校验内层运行标识。原记录不接受其他运行的完成状态。
4. **数据库未采纳结果，协调流程却退出。** 聊天和定时协调器都检查条件更新实际影响行数；未写入的终态不会结束后台工作流。原生运行标识仍由条件更新保护。
5. **暂停队列、审批等待与实际运行混淆。** 聊天对原生待审批显示等待授权；暂停队列返回明确待处理原因，保留原会话的“开始处理/移除”入口。未知结果的宿主恢复最短间隔三十秒，执行连接忙时不抢占、不把核对操作加入其他运行的队列。
6. **终态仍残留待审批/成果收集中。** 即使过程记录已与终态同名，读取仍清理 pending/submitting 审批的可操作状态，将尚未确认的成果状态标为 unconfirmed；不会把没有收集证据误报为无文件。聊天有过程记录时也可展开失败/待核对原因。

主要实现位于独立宿主 `host/dock-host.ts`、`host/host-activity.ts`、`host/dock-runtime.mjs`；Hutian 的 `chat-dispatch.ts`、两个协调器及消息失败详情。未新增业务表或迁移，未替换运行身份、原消息、原回执和冻结配置；不是新建另一套执行引擎。

## 验证与线上观察

- 使用当前实际源码的隔离诊断核对 11 个聊天分支：原记录缺失、外来已回复运行、暂停队列、待审批、连接忙、恢复节流、原运行续查、交付失败、正常回复、取消排队与首次派发。
- 核对 10 个宿主交付/过程分支：空正文、仅过程文本、输出/轮次限制、拒绝、空白最终正文、超长 Unicode 正文、原最终正文、同名终态的残留审批/成果状态，以及原生完成与交付失败分离。
- 聊天和定时的条件更新分别复现影响零行/一行；零行均不会退出协调。原运行/Provider/内层运行不匹配均拒绝，正常回执和不带内层 ID 的原生错误保留兼容。
- 实际当前库核对：106 条聊天请求（95 已回复、10 取消、1 失败）、17 次定时运行（8 已回复、2 跳过、7 失败），没有残留活跃/待核对记录。既有失败与取消没有改成成功。
- 真实浏览器读取 ZCode 原会话、Runtime 和原验收附件，下载 HTTP 200、正文为原 `ZCODE_HUTIAN_OK`。当前工作为零，没有浏览器 pageerror。
- 失败原因展示另用浏览器拦截响应模拟，不写后端、不发送消息；有过程记录的失败原因可展开，390px 无横向溢出。此项是 UI 异常状态验证，不声称真实运行触发了输出上限或模型拒绝。
- API/Web 类型检查、构建、宿主 `pnpm check`、本轮文件 ESLint 通过。Web 原子更新资源，在执行宿主空闲且队列为空时由原 launchd 服务加载 API/宿主修复。Dock 本轮未修改或重启。

诊断脚本和结果仅保留在两个项目忽略目录 `.local/runtime-chain-audit-20261118/`，未新增永久测试、框架或依赖；本轮没有新模型调用、工具重放、审批提交或重发原用户消息。修改仍属第 7 段，本轮源码按用户授权整理提交并推送；未发布 App/SDK。

## 保留的真实边界

没有原生终态证据的断线或进程故障仍为未知，不能靠超时改成成功或确认取消。ZCode 未声明原生结果查询，设备失去已保存证据时不保证自动恢复；不会为了清除“待核对”重发提示或工具。文件收集失败仍提供补取原成果入口，无法确认的文件不显示为已交付。本轮没有重新制造设备故障或执行真实拒绝/超限请求，也未重验 Windows。
