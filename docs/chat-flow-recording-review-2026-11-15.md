## 私聊：从发送到结束

| 发送后 | 实际看见什么 | 判断 |
| --- | --- | --- |
| 0–0.4 秒 | 输入清空，原历史仍在；随后新消息出现 | 短暂提交间隔存在，不能等到有 run 才建立稳定的响应位置 |
| 0.4–2.4 秒 | 已发消息下面出现“请 Mac 验收助手处理这条消息”，输入框上方另显示准备资料；当时正在自动提交 | 恢复入口过早出现，即便禁用，也容易理解为还要再点一次 |
| 2.4–4.5 秒 | 状态先在用户消息下面显示“已接收／正在处理”，之后才变为带头像的助手回复 | 同一项工作更换位置和呈现形态，缺少连续的回复区域 |
| 6.8–13.5 秒 | 静态“已连接运行环境，等待执行端输出” | 此时原生尚未给内容；需要准确等待反馈，不能虚构正在读文件或正在思考的进度 |
| 13.5–20.3 秒 | 进度文字、三条工具、后续说明分批出现；顶部常驻原始模型 ID、`推理 high`、“原生会话已接收配置” | 技术诊断混入默认阅读路径；第一段说明几乎整段出现，三条短工具一次进入完成态 |
| 21.5 秒 | 最终表格还只有部分内容，整个过程已自动收起，状态仍为“处理中”，停止仍可见 | 收起触发条件过早；内容高度一次减少约 119 px，滚动跟随一起变化 |
| 22.6–23.7 秒 | 答案完整后仍短暂显示处理中；随后出现耗时、复制／引用／保存，停止恢复发送 | 需要区分生成答案与完成交付，避免多个控制区各自切换；当前没有稳定统一的收尾 |
| 结束、刷新 | “本次参考”仍悬在输入框上方；刷新后消失，正式答案保留 | 来源归属在页面临时状态，没有作为这轮回复的可恢复信息呈现 |

流式输出并非完全不存在：原生最终答案有多条 `text_delta`，浏览器实际只出现两次正文增量，然后转为完成态。当前每次读取整份会话快照，再等待一秒，增加了块状更新的感觉。不能把首字前的模型等待全部归因于前端，也不能用逐字动画掩盖真实数据节奏。

同日再次核对：服务端文件已随并行后端整理迁至 `apps/api/src/modules/workbench/http/chat-events.ts`，仍采用 `readConversation` 全快照与 `delay(1000)`；浏览器 `EventSource` 合并快照，`projectActivity` 累积公开 `text_delta`。因此当前有真实增量展示能力，但尚未完成及时传递、稳定渲染和收尾一致的端到端流式体验。流式是本轮必须修正的主路径，除文字增量外还要验收未完成的 Markdown／代码块／表格持续增长、工具状态更新、手动阅读期间不抢滚动、最终文本落地不闪烁或重复；不能以 SSE 接通或假打字动画判定完成。

## 群聊增加的问题

1. **排队对象不清楚。** 同时点名两位后出现通用“已排下一轮／移除”，没有在这行明确标出 Windows；很像用户又排了一条消息，而不是同一条点名请求中的第二位成员等待执行入口。
2. **回复顺序在过程中反转。** Mac 先完成；Windows 开始时，运行中的回复插在 Mac 已完成答案前面。Windows 完成后，正式答案又移到 Mac 后面。发送后约 22.4 秒和 145.3 秒的 DOM 与截图确认该变化。用户正在阅读的顺序被打断。
3. **长等待反馈不足。** 发送后约 26.7–137.5 秒，Windows 一直显示“已连接运行环境，等待执行端输出”，约 111 秒无新的可读反馈；随后才出现 WebSocket→HTTPS 回退说明。Windows 执行本身约 123 秒，网络问题仍存在，单改页面不能消除该耗时。
4. **正常收尾闪现异常操作。** Mac 只需文字回答，发送后约 19.1 秒却短暂出现“成果文件待核对／补取原成果”，约一秒后消失。后台收取的 pending 被直接呈现为用户需要核对；本轮最终没有文件交付。
5. **参考列表重复。** 输入框上方出现两个同名“会话工作记录”，没有解释各自归属。两个成员来源简单合并后输出，既不属于输入内容，也不清楚对应哪位的已完成答案。

## 已定位的实现原因

| 问题 | 当前源码位置 | 修正方向 |
| --- | --- | --- |
| 初始恢复按钮与状态分散 | `apps/web/src/components/communications.tsx`：`retryTargets`、`UserMessage`、`preparing` | 提交未确认、正常准备、真正失败恢复明确区分；同一成员从接收起就有稳定的工作区域 |
| 群聊前后换位 | 同文件 `messages` 投影：`return [base, ...working]`；运行中用 `run:` 标识，完成后替换为 Matrix 消息 | 沿稳定请求／运行关联做统一展示；正式消息仍遵守 Matrix 顺序，不通过改写时间或消息事实修补 UI |
| 大块刷新 | `apps/web/src/app/api/chat-events/route.ts`：整会话快照＋`delay(1000)` | 优先沿已有原生活动与 SSE 接口增量送达，保留顺序与重连补读；不新增第二套消息账本 |
| 首段最终答案就收起 | `apps/web/src/components/chat-execution.tsx`：`manual ?? !(terminal || projection.final)` | 让答案生成与已完成成为不同状态；只按已确认结束自动收尾，用户手动开合优先 |
| 运行态分裂 | `communications.tsx` 的 assistant-ui runtime 固定 `isRunning: false`，另叠自定义运行状态 | 按每位成员、每轮请求映射真实状态；不能简单把整个群聊全局设为 running 来替代逐成员控制 |
| 正常收尾提示补取 | `chat-execution.tsx` 同时把 `outputsState: pending / unconfirmed` 显示为“成果文件待核对” | 区分正常收取、真正未知、明确失败、无文件；真实未知才开放核对，不在正常收尾闪恢复按钮 |
| 来源归属错误 | `communications.tsx` 的页面级 `references` 和 Composer `before` | 来源绑定实际请求／回复，按真实资源与来源去重，刷新后能恢复；输入区只说明下一条消息将使用什么 |
| 诊断信息与动作过重 | `chat-execution.tsx` 默认展开请求参数；私聊同时有运行旁停止与输入框停止 | 常态突出进度与正文，参数按需查看；私聊明确一个主要停止入口，群聊保留各成员自己的停止 |

以上是定位与修正方向，本轮尚未修改这些业务行为。诊断行、参考列表、队列命名等涉及产品取舍，不能只移动控件就视为闭环。

## 五个视角的审查结论

| 视角 | 当前问题及证据 | 应采取的产品决定 | 如何判断改善 |
| --- | --- | --- | --- |
| 产品 | 用户只做了“发给一位／两位成员”一个动作，却先后看到请求准备、恢复按钮、排队、运行块、正式消息等不同对象；群聊排队又被叫作“下一轮” | 页面围绕“某位成员对这条请求的回复”组织；内部的 request、job、run、delivery 只推动同一区域变化。区分成员等待与用户追加的下一条消息 | 发送后无需再次点名或点击处理；始终能判断谁收到、谁等待、谁需要我介入 |
| 设计师 | 同一工作换位，过程与结果视觉权重接近，原生参数常驻；自动折叠改变高度，阅读顺序反转 | 结果为主、过程为辅、诊断按需；稳定布局与滚动锚点先于装饰。审批／问题单独突出；运行、完成、手动展开都有明确布局 | 结束前后不重挂整段回复；向上阅读／选中文字时不被拉走；正文不用穿过参数和恢复操作才能看到 |
| 技术 | 运行与正式消息使用不同 ID／投影位置；全会话每秒快照；`final` 存在即折叠；pending 当 unconfirmed 展示 | 建立基于原请求关联的统一展示投影，消费真实有序事件，分别表达执行、回流与连接状态 | 顺序不反转，增量不重复／丢失，重连不创建新运行，文件收取不改变已完成文字回答的状态 |
| 老板 | 这是每次使用都会经历的主路径；功能增加已经快于基本体验稳定，成功回执掩盖了反复确认和信任成本 | 本轮优先把既有聊天闭环做可靠；复用 Matrix／Dock／DBOS 和现有组件，集中三次小交付；暂不拆新项目或增加管理入口 | 用相同真实工作比较前后录屏；消除额外点击、重复发送诱因和阅读中断，再继续扩展功能 |
| 用户 | “是不是没发出去”“为什么又要请他处理”“Windows 卡了吗”“发下一句会停掉谁”“结果跑到哪里去了”都需要猜 | 每个状态有清晰主体、可理解的原因和可执行的下一步；默认动作保持简单，异常时保留输入和已返回结果 | 不理解 Runtime／run 也能完成发消息、等待、补充、停止和取结果；多成员时不会误作用于另一位 |

以上是基于本轮两条真实路径的判断，不是用户留存或满意度统计。窄屏、长文本选取、审批中跨会话切换等未在本轮重新完整录制，属于下一轮必须检查的关键分支，不能伪装成本轮已经复现的缺陷。

## 交互设计专项裁决：默认阅读路径放什么

用户随后圈出“本次请求：成员默认／设备／模型／推理／原生会话已接收配置”和输入框上方“本次参考”两处。重新查看实际截图与渲染代码，确认两者分别由运行配置和 `askConversation` 返回的 references 直接呈现，不是助手正文引用。上一版虽然定位了问题，但设计方案还需要明确哪些信息应退出默认视线，不能只改成更小、更灰的字。

| 信息 | 正确归属 | 默认表现与展开入口 |
| --- | --- | --- |
| 成员当前 Runtime、模型与推理设置 | 成员设置；私聊保留已批准的顶部快捷入口 | 不在每轮正文重复；修改仍只作用于后续请求 |
| 这一次实际请求的配置快照、执行端确认、连接诊断 | 这轮回复的运行详情 | 从回复菜单按需查看，保留历史核对能力。正常“已接收配置”不展示成进度；不支持或确实未生效时才就近提示影响与处理入口 |
| 用户主动附加的文件、明确选择的资料 | 发送前输入内容、发送后该用户消息 | 使用具体名称和附件状态；可查看或移除，不能用笼统的知识库类别代替具体附件 |
| 是否允许参考知识库／记忆、可用资源范围 | 输入工具菜单中的选择项 | 属于设置开关，不能使用与附件相同的可删除 chip 外形，让人误认为已经附加某份资料；保留现有开关能力及范围规则 |
| 本轮检索到并提供给某成员的资料 | 此成员的过程／详情 | 按需查看“检索资料”或“提供的上下文”，不使用 `[1][2]` 伪装成答案引文，不占下一条消息的输入区 |
| 回答明确引用的来源 | 答案对应段落或答案底部 | 使用可追溯引用；没有引用事实就不生成编号，不能从检索列表推断模型采用了全部资料 |

具体设计问题还有：

- **注意力顺序错误。** 当前正文、技术信息和高亮来源同时争夺注意力。默认阅读顺序应是需要我处理的事项、最新进展／答案、可查看的过程，诊断最后。已有上下文不需要每轮再向用户宣告。
- **操作语义互相干扰。** 空输入的“排下一轮”下拉紧贴停止按钮，组合看起来像同一个动作的选项。空输入时隐藏无用途的发送模式；有内容时让“排队发送／补充当前工作”与实际主按钮对应。
- **停止重复。** 私聊回复右上和输入框同时提供停止，既增加注意点，又让人猜作用范围。私聊保留一个稳定控制位置，群聊将控制附着到具体成员；输入内容变化不能使停止失去可发现性。
- **工具缺少阅读摘要。** 原始命令直接成为主标签，普通用户需解析 `/bin/zsh -c`。有真实语义时显示“检查系统版本／检查 Node.js／检查磁盘空间”；原命令与输出展开查看，不能用模型猜测覆盖真实操作。工具行做紧凑分组，短任务无需制造逐条动画。
- **阅读密度不平衡。** 录屏中正文较小，消息、工具和动作之间却有较多空隙；应按长文本阅读调整聊天局部字号、行宽和间距，保留项目主题。候选正文 14–16 px 需在实际尺寸下对比后确定，不直接修改全局设计 token。
- **结束动作过重。** 复制、引用、保存、请另一位继续全部同权重常驻，每条回答都像操作表单。保留常用轻量动作，保存与交接进入次级菜单；键盘聚焦可发现，不仅依赖鼠标 hover。
- **时序变化破坏空间关系。** 运行转正式回复、折叠过程不能让正在阅读的内容换位；这是交互设计验收要求，不能只依靠过渡动画掩盖。

本专项与上一节五视角结论共同构成待实施方案；只调整默认信息层级与动作归属，不删除追溯数据或既有能力。原型旧版本的开合状态不能证明当前正式页面已经达到本方案。

## 统一交互方案

### 1. 发送前：输入是主要入口

- 私聊直接输入；群聊／频道用结构化 `@成员` 确定处理者，无点名仅发普通消息。同名成员、删除提及、粘贴纯文本及键盘选中都需要明确规则，不能只用显示名字匹配身份。
- 输入上方不常驻来源列表、执行参数或说明墙。正文下面保留已附文件／选定资料和紧凑工具栏，`+` 收纳附加动作；待上传、失败和可移除状态依附相应附件。
- Runtime／模型／推理仍属于成员；群聊通过成员入口设置，私聊顶部保留该成员快捷设置。正在运行和已排队请求沿冻结快照，不因后来设置修改而变化。
- Enter 发送，Shift+Enter 换行；中文输入法确认和 `@` 候选选择优先于发送。发送失败保留可恢复内容、引用与现有附件记录；不扩建草稿管理。

### 2. 发出：立即反馈，一次动作

点击发送后当帧反馈“发送中”，用原提交标识与 Matrix 正式消息对齐。只有确认消息／请求接收后才显示“已接收”，不把本地预告当作执行成功。请求暂未拿到 run 时，也有稳定的成员回复位置。

正常链路不显示“请某某处理”恢复按钮。消息保存失败显示“未发送 · 重试”；消息已保存但成员请求未成功显示“某某未开始 · 重试请求”，重试沿原操作标识，不复制消息、不重复执行。

群聊同一请求的成员回复按请求中的稳定顺序定位，例如 Mac 在前、Windows 在后；排队的 Windows 就在自己的位置显示“Windows · 等待执行”，不在 Mac 完成后又插到它前面。后续用户消息正常追加。最终消息填入原回复位置，原事件 ID、作者、真实时间和引用关系保留。

这采用按发起消息组织成员回复的展示方式；不修改 Matrix 时间或原始事件顺序。历史、实时和刷新使用同一投影规则，避免只在当前页面稳定、刷新又改顺序。

### 3. 等待：说明谁在等什么

| 真实阶段 | 对用户显示 | 操作与约束 |
| --- | --- | --- |
| 请求已接受，尚未执行 | `墨菲 · 已接收` | 不同时显示“请处理” |
| 等待入口 | `墨菲 · 等待执行`，有可靠数据才补充队列信息 | 可取消这位成员的未开始请求；不取消同消息中的其他成员 |
| 准备上下文／连接 | `墨菲 · 正在准备`或`正在连接运行环境` | 随真实阶段更新，完整参数放详情 |
| 执行已确认但暂无内容 | `墨菲 · 等待回复 · 18 秒` | 计时只说明等待时长，不伪造思考或工具动作 |
| 已有公开进展 | 展示实际进度文字和紧凑工具行 | 活跃工具有状态；短工具可能直接完成，不为了动画延迟真实结果 |
| 长时间无新输出 | `仍在等待回复 · 最近输出在 45 秒前`；若从未输出则明确“尚未收到输出” | 可查看详情／停止；仅有超时、断线等真实证据时显示连接异常 |
| 需要批准／回答 | 对应成员的明确请求及实际操作范围 | 独立于可收起过程；提交中、已提交、原生接受分别显示 |

长等待提示建议在持续 15 秒无内容后增加计时说明，持续 60 秒后突出查看详情与停止；这是候选展示阈值，需录屏评估，不是执行超时或自动重试规则。连接是否健康必须来自连接观测，不能从“没有新文本”反推。

### 4. 返回内容：边到边读，位置连续

- 一条成员回复包含：成员身份与状态、可展开工作过程、最终正文、真实成果／来源、结束后动作。只包含纯文字回答时不制造空的过程区域。
- 公开进度与工具进入过程；最终正文出现后单独增量显示。出现第一段最终文字仍可能继续生成，不能就此折叠、显示完成或恢复下一轮。
- 执行参数、连接重试原文与调试信息放“运行详情”；确实影响用户时，以短状态说明当前影响。模型／设备 ID 不成为每次聊天都要读的一行。
- 已明确的结果正文、图片和文件不能因后来又调用工具就消失。缺少可靠 phase 时保留正文，不能用“只留下最后一段”猜测最终回答。
- 用户在底部时跟随增量；主动向上滚动或选择文字后停止跟随，提供回到最新入口。过程开合、表格增长、工具完成和消息落地使用同一锚点规则，避免整段回复重挂。

### 5. 结束：正文稳定，过程可回看

只有收到权威终态，才进入结束状态。成功后默认收起公开过程为“用时 20 秒”；用户主动展开过则保持选择，正在选取过程文字时延后自动收起。过程收起不改变正文的阅读锚点。

文字已完成、文件仍在收取是两个事实：已有文字立即可读，文件区域显示“正在收取文件”；没有文件预期时不显示空文件卡。正常 pending 不能出现“成果待核对／补取原成果”。真正回流未知才提供核对原运行，明确失败才提供相应恢复。执行停止／失败不能标成成功；部分输出保留，继续与重试的含义分开。

复制／引用是常用动作；保存结果与人工交接收入次级菜单，但保留已有能力。尚无正文时不显示无效操作。保存、下载与复制失败都在实际动作处反馈，不能用点击本身冒充成功。

来源随对应回复保存和恢复：区分“提供给此成员的资料”和“回答明确引用的来源”；检索返回不能证明模型引用过。多个成员的来源不合并成输入框上方的无主列表，同标题不同来源也不误合并。

### 6. 运行中继续输入：动作和对象都明确

| 情况 | 默认动作 | 另一个明确入口 |
| --- | --- | --- |
| 私聊空闲 | 发送给当前成员 | 无需先选择处理者 |
| 私聊运行中、输入为空 | 主要按钮停止当前工作 | 不在回复和输入框重复两个主要停止按钮 |
| 私聊运行中、输入有内容 | 排下一轮，按钮名称／提示清楚表达 | 可改为“补充当前工作”；输入非空时，唯一停止入口保留在输入工具栏，不因打字失去控制 |
| 群聊 `@A @B` | 分别派发／排队，两人的状态各自可见 | 停止依附对应成员；不提供语义含混的全群停止 |
| 给运行中的某位补充 | 必须明确一个目标运行且它支持补充 | 不支持时保留内容，提示可排下一轮；不能静默改成停止重启 |
| 移除下一条排队消息 | 取消指定待执行请求，保留消息与取消事实 | 不撤回已经执行的副作用，不影响其他成员 |

模式选择只在存在可用替代动作且输入有内容时出现，避免空输入也常驻大下拉。服务器确认补充已接收后才显示接收；送达未知保留原操作并可核对，不再次新开运行。停止后同会话已暂停队列仍沿现有人工恢复规则。

## 技术落地与责任边界

1. **统一展示身份。** 优先使用现有 `chat_request.id` 关联触发消息、目标成员、job、run 与回复事件。接受前可用带命名空间的客户端提交 ID，接受后关联但不更换已挂载的展示 key。仅用成员 ID 匹配会混淆同一成员的多轮请求；补充属于原轮，显式排队才产生新轮。
2. **一个展示投影。** 将散落的 preparing、retryTargets、working placeholder、正式回复统一为逐成员的状态投影。业务权威继续来自原模块，不新增浏览器业务队列或第二套消息账本。原正式回复仅渲染一次，历史和实时沿相同关联恢复。
3. **状态分别建模。** 消息提交状态、成员执行状态、输出收取状态、观察连接状态相互独立；UI 根据组合选择一个主要阶段。`finalText.length > 0` 不是完成信号，`outputs.pending` 不是失败，SSE 断开不是任务停止，工具退出非零也不自动等于整轮失败。
4. **真实增量链路。** 核对 Dock → 宿主 → Hutian → 浏览器各段事件时间和游标，再将已有活动事件及时转发；消息历史仍由 Matrix 补读。首屏／重连用快照校准，后续按事件 ID／序号去重；必要时微批文本，但不逐字播放已完成的整段答案。事件缺口沿原运行补读，不能重新派发。仅把一秒轮询改成 100 ms 全量轮询不作为最终方案。
5. **复用已有组件。** assistant-ui 管消息、输入和滚动，Beautiful UI／Radix 管过程与工具。修正适配状态而非再叠一套相互冲突的全局 loading；群聊不通过一个全局 `isRunning=true` 表示所有成员的状态。
6. **幂等控制。** 重试提交、批准、停止与补充沿各自原操作标识；状态未知先核对，明确不存在时才允许重试派发。部分成员失败按成员恢复，避免一键重复整组已完成工作。
7. **来源与成果。** 从现有冻结上下文和收取记录恢复本轮来源；需要补字段时放在原请求／交付关系，不复制整份资源库。访问时沿原权限校验，撤回的来源显示不可访问，不能用浏览器旧缓存绕过范围。

预期主要修改 `communications.tsx`、`chat-execution.tsx`、会话 SSE 和原请求／活动投影；是否需要 Matrix 宿主透传接口，须按增量链路实测确定。Dock 原生模型、权限和全局配置不因这次 UI 方案改变。连接回退造成的真实等待另行定位；本方案保证等待可理解，不承诺降低模型本身耗时。

## 实施顺序与验收标准

沿当前第 7 段拆成三次小交付，不另起平台重构或独立子项目。下面是建议实施顺序，尚未开始本轮业务修改。

| 顺序 | 可交付结果 | 最短真实验收 |
| --- | --- | --- |
| 1：先把一轮对话固定下来（P0） | 统一回复身份／顺序、发送反馈、成员队列归属、结束与文件收取状态；去掉正常提交中的恢复按钮 | 重跑本报告私聊与 Mac／Windows 群聊；全过程没有换位／重复块／假失败，刷新顺序一致；一位完成时另一位状态不受影响 |
| 2：把过程呈现和控制做顺（P1，属于本轮闭环必需） | 真实增量、阅读锚点、过程开合、单一主要停止入口、补充／排队语义与来源归属 | 工具＋长正文；上滚／选取期间继续输出；生成中补充、排队、停止；一次真实审批；已有成果保存／预览／下载；恢复原会话后不重复运行 |
| 3：连续使用收尾（P1） | 发送失败、部分成员失败、长等待、观察断线和终态恢复一致；键盘／中文输入及紧凑尺寸可用 | 以现有能力走最短异常路径，Mac 和 Windows 各验证，连续录制并对比关键时间点，不建立新测试工程 |

候选体验门槛：点击或快捷键提交的本地反馈不等待网络（目标 100 ms 内）；原生事件已经到达宿主后，正常本机链路浏览器可见增量目标 300 ms 内，必须分段测量后报告，不包括模型尚未产出内容的时间；相同操作不产生重复消息或运行；用户上滚时强制拉回次数为零；同一回复在运行／落地／刷新后的顺序一致；正常无文件文字回答不出现补取按钮。上述目标是待验收指标，本轮没有宣称已达到。

保持当前已有资源、配置、审批、保存与人工交接能力；本轮不增加草稿管理、自动选人、并行调度、项目管理、全局新主题或新的独立开源项目。交付结论必须同时写清实际通过的路径与未覆盖的分支，最终截图和成功回执不能替代完整流程录屏。
