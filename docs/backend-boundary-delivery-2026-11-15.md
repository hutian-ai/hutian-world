# 前后端边界交付

2026-11-15，现有第 7 段的追加调整，保持未提交；没有推送或发布。此前的[边界审计](backend-boundary-review-2026-11-15.md)已落实到代码和本机运行服务。

## 现在的结构

| 部分 | 实际职责 |
| --- | --- |
| `apps/web` | React/Vite 静态前端，React Router 保留原页面 URL，浏览器通过 API 获取数据与提交操作 |
| `apps/api` | Hutian Server：身份、业务、授权、资源、工具、上下文、文件、事件及后台协调 |
| Matrix Agents Chat 执行宿主 | 保留原应用身份和连接，持有原生执行、队列、回调与文件回流链路 |
| Matrix / Memory Access / 知识服务 / Dock | 继续保存各自负责的权威数据 |

没有新增通用 Server 或独立转发网关。Web 本机的 `scripts/serve.mjs` 仅提供静态文件与同源反向代理，不读取应用凭据、不运行业务，也不处理后台作业；`dist/` 可由其他静态服务器部署。

## 已迁移内容

- 原 Web 中的资源接入、角色及会话资源授权、工具定义与调用、偏好引用、对话摘要和后台提取。
- 聊天消息与运行派发、角色通信身份、人设快照、执行选项校验、补充／停止、队列、人工交接及成果保存。
- 设备查询、Dock 凭据导入、模块连接归属与资源空间准备。
- 上传、原输入附件、执行输出、报告附件、历史分页与 SSE 状态流。
- 定时安排的执行协调。`apps/api` 的后台工作直接调用应用服务，保留原用户与空间上下文，不再回调 Web，也不通过管理员凭据自调用 HTTP。
- 原生任务客户端从 `apps/web/scripts/task-client.mjs` 移入 `apps/api/scripts/task-client.mjs`。脚本内容和既有只读审批策略保留，本机受管配置与初始化脚本使用新位置。

应用接入集中在 `apps/api/src/modules/workbench/`：`services/` 保留现有业务适配，`application.service.ts` 连接既有领域服务，`commands.ts` 是前端可调用操作的显式白名单，`http/` 与 transport controller 处理文件、事件和工具回调。后端注册表与 `packages/contracts/src/workbench.ts` 的公开请求响应类型进行编译核对。内部 helper 不作为任意远程函数暴露。

原业务模块继续负责身份、角色、项目、安排、运行请求及其数据库事务；`workbench` 不另建这些状态的副本。DBOS 名称、schema、工作流标识，原 Matrix 身份／消息，资源标识和 Dock 回执保持原值。本轮没有数据库迁移或数据重置。

私有应用数据路径由 API 的 `config/paths.ts` 相对模块位置确定，不再依赖 Web 目录或进程启动目录。

## 浏览器与 Agent 授权

浏览器从 API 建立签名的 HttpOnly / SameSite=Strict 会话。后端检查本机 Host、请求来源及当前有效身份；应用级 Bearer 和 Matrix / Dock / 记忆 / 知识凭据都不进入浏览器。此入口沿用可信本机单创造者身份，并不是新增多人登录体系。

浏览器使用显式白名单中的应用命令。含本轮工具授权的原始运行快照、角色通信身份绑定和安排消息回执绑定仅接受服务端应用凭据，不能通过浏览器会话直接读取或写入。

Dock 继续按次向 Agent 注入 `hutian_context` 工具，回调地址改为 API 的 `3341/api/context-tools`。工具回调独立验证本轮授权，重新核对空间、用户、连接、角色与会话范围。原生执行仍由原宿主持有；未修改原生模型、全局权限、配对或两端安装。

独立 Codex 可配置的通用 Hutian MCP 入口仍不是本轮交付。当前是 Dock 会话注入的 MCP 工具桥，业务已经统一到 API。

## 2026-11-16 前端更新后的页面加载修复

用户在已打开的标签页进入运行环境时，看到泛化的“请确认应用和数据库已启动”。实查 Web、API、执行宿主正常，新开页面能够读取 Dock 目录与在线 Mac。

在独立浏览器中用隔离构建目录复现：保留旧页面入口，构建清空带哈希的旧资源后，点击运行环境请求旧版页面及其依赖，得到 404；旧“重新加载”只重新验证路由数据，浏览器保留失败的模块导入，仍停在错误页。完整页面刷新能够恢复。隔离复现未清理正在服务的目录。

修复为 Vite 构建保留既有带哈希资源（`emptyOutDir: false`），让更新前打开的标签页继续使用同版模块；HTML 仍按原静态入口 `no-cache` 提供。路由区分页面资源加载失败和 API 读取失败：前者提供完整页面刷新，后者保留读取重试及明确接口错误，不再统一误导为数据库未启动。不自动刷新正在编辑的页面。

实际验证：打开更新前的收件箱，再构建更新，83 个原资源保留，原标签页导航到运行环境成功且无页面脚本或 HTTP 错误；在独立标签页拦截页面资源为 404，显示资源错误，解除拦截后点击“重新加载页面”恢复真实 Runtime 目录。类型检查、构建和相关 lint 通过。未更改 Dock 配对、连接身份、模型或权限；仍属第 7 段，保持未提交。证据在 `.local/runtime-page-recovery-20261116/`。

## 前端更新流程防护

用户追问如何避免再次发生，继续将资源保留修复落实到构建入口。以下流程取代直接在 `dist/` 内增量构建的临时方式：

1. `pnpm build` 中的 Web 步骤或 `pnpm --filter @hutian-world/web build` 调用 Vite 官方构建 API，在 `.local/web-build/` 下的唯一临时目录生成完整产物。
2. 检查 Vite manifest 的入口、静态／动态依赖和资源文件。构建或资源校验失败时，不切换当前入口。
3. 通过目标文件系统内的临时文件加 rename 安装完整资源，保留旧哈希资源；全部完成后，最后原子替换 `dist/index.html`，HTML 写入构建版本用于核对。
4. 保存上一版 HTML 入口，可用 `pnpm --filter @hutian-world/web rollback` 恢复。回退只覆盖前端，不承诺 API／数据库版本回退；旧资源目前不自动清理。
5. 直接运行 `vite build` 只写隔离预览目录，不写正在提供服务的 `dist/`。纯前端更新不重启后台，也不自动刷新用户正在编辑的标签页。

已实测：更新期间 52 次 HTTP 读取均为完整旧／新 HTML；186 个既有资源保留，已打开的收件箱在更新后进入 Runtime 目录，无页面脚本或 HTTP 错误。对真实 Vite 产物移除一个入口依赖后，发布被拒绝且当前 HTML 不变。前端回退及恢复最新版均逐字核对通过；三项服务 PID 保持不变。当前真实目录报告 Mac 与 Windows 都在线（仅代表本次读取）。脚本语法、相关 lint 和 diff 检查通过；未新增测试工程、CI、依赖或服务。证据位于 `.local/frontend-update-20261116/`，仍保留第 7 段未提交改动。
