# 运行状态与原回执修复（2026-11-17）

本轮修复状态查询和结果交付，改动留在本地未提交。没有新增测试工程、修改任务周期或重新生成日报。

## 已确认的问题与修改

- 交互执行回执保存 `config` / `tools`，CLI 却只接受基础四个输入字段。Dock client 的回执读写现在使用一致校验，保留原身份、私有文件权限、原 runId 和输入；Matrix bridge 明确列出可保存的字段。
- 原生最终回答已经收到，但 Dock 可能仍记录 `unknown`。增加显式 `status --reconcile`，Matrix 回查使用此入口，仅在原快照为 unknown 时读取同一原生 turn，再读取 Dock 更新后的快照。原生读取失败仍保留原观察，不重发 prompt、工具或审批。
- 宿主只读 `status.stdout.json`，漏掉首次运行保存的终态。现在可回退读取 `run.stdout.json`，忽略损坏或不属于当前运行的观察；明确的失败、取消和已交付状态优先于旧查询错误。
- 无效 JSON、运行标识不符、状态不符、查询命令失败和回执不兼容分别处理。完成后清除旧的查询错误，执行事件异常明确显示需要核对，不再一律提示等待重试。
- Dock 原始 ACP 消息和 ACPX turn 队列的生命周期不同：ACP prompt 返回后，保留会话会切到 idle projection，迟到的会话元数据不一定出现在 turn 队列。驱动现在只允许丢弃**匹配当前 session/prompt 响应之后、属于同一 session 的尾部 session_info_update**；运行中缺失、错序、身份不符及未匹配的正文／工具事件仍报错，完成状态仍以 ACPX 原终态为准。

## 实际核对

- 原故障记录的回执包含 config，旧查询日志为 `invalid_run_receipt`；原执行结果为 `acp_update_order_mismatch`。使用修复后的回执读取成功。
- 原生只读核对返回 completed，随后正常后台协调沿原运行交付，Matrix 回执为 replied。实时状态接口与会话接口均确认完成、无错误，原正文保留；没有重跑报告。
- 原故障未保存原始 ACP 通知队列，因此无法从旧记录证明当时具体哪条通知错位；本次修复覆盖已定位的收尾生命周期边界，不宣称所有同名异常均属此原因。
- 19 项相关既有检查通过（ACP 队列、扩展、DSH 与执行 CLI）；另在私有目录做了晚到元数据、错误 prompt 身份、运行中缺失事件、未匹配工具事件和原回执的临时核对。没有新增仓库测试代码。
- 使用修改后的 Codex 驱动实际执行短消息，收到最终文本且终态 completed。Matrix 类型检查、构建及 Dock client/driver 构建通过。
