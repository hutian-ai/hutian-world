## 1. 先确定的产品结论

**默认使用方式：选一个角色，直接说要做什么；角色在这条聊天里工作，需要你时在原处提问或请求授权，结束后留下清晰答案和真实成果。** 不要求先选择“讨论”或“执行”，也不要求先建项目、任务卡或工作流。

1. 单角色聊天以 Codex 的“公开进度／工具活动／交付回答分层”作为主参照。进行中看得到工作；常规最终回答开始后，过程可自动收起；用户主动展开优先；待处理问题和成果不能被收起后消失。
2. Cindy、ZCode 用来核对活动与成果如何区分，agentes-chat、Multica 用来核对会话、角色、运行和设备的关系。各产品机制不同，不以拼接组件代替统一规则。
3. 当前最主要缺口是从 Runtime 到聊天的事件与控制闭环。Dock 已有多项能力；Matrix 宿主和 hutian 页面需要接通，不能只改显示层。
4. 后台可靠性是本轮完整方案的一部分。建议在交互接通后，小范围采用 DBOS 管理业务派发、等待与恢复；保持 Matrix 的消息权威、Dock 的执行权威。不整体迁移旧 hutian 的世界引擎。
5. 先达到日常工作可用：资料研究、写作、现有执行环境中的代码修改与文件交付、周期工作、人工交接。自主找人、自动拆派任务、项目管理、完整 IDE 与跨 Runtime 在途迁移继续后置。

这能逐步替代用户通过 Codex 完成的一部分日常工作入口，但“聊天体验接近”不等于完整平替 Codex。工作区选择、代码差异审阅、原生工具与登录、Skills、浏览器／桌面能力、模型特性仍受实际 Runtime 和接入契约限制。本文明确哪些进入本轮，哪些需要后续交付，不用一个“已对齐”覆盖全部。

## 2. 用户如何使用

### 2.1 一次完整的私聊工作

以“帮我核对这份研究笔记，整理成一份带出处的结果”为例：

| 用户操作 | 页面反馈 | 系统实际行为 |
| --- | --- | --- |
| 从沟通进入研究员私聊 | 看见历史、输入框、当前角色；默认 Runtime 已配置时无需重复选择 | 校验当前身份与会话；首次使用缺少执行入口时就地引导选择 |
| 选一份资料或上传文件，输入要求 | 输入框显示所附资料，上传／处理状态可见 | 资料保留来源和可用范围；未就绪资料不冒充已提供给模型 |
| 发送 | 用户消息先显示发送状态，再出现本轮工作 | 先保存通信消息，再以稳定请求身份派发；两个确认分别处理 |
| 阅读进度 | “正在核对引用”等公开说明与真实工具活动按顺序出现 | 原生事件经宿主投影，不人工生成“思考过程”或假的工具步骤 |
| 补一句“只保留原始来源” | 当前补充显示“待接收”，收到回执后变为已补充 | 能力允许时送到同一原运行；不停止后重跑，不暗中变成下一轮 |
| 回答澄清问题／处理审批 | 当前角色的提问或操作范围就地出现 | 答案与授权分别提交；“允许”只表示决定送达，后续仍等待工具结果 |
| 最终答案开始 | 常规过程收成“用时 …”入口，回答在下方出现 | 根据消息阶段投影；手动展开不被新事件覆盖 |
| 本轮结束 | 回答与真实附件可读，出现完成操作；可展开查看过程 | 原运行终态、最终文本与附件回流各自确认，失败不能用完成样式掩盖 |
| 继续修改结果 | 仍用同一输入框：“把第三段改成表格” | 新一轮沿原会话与获准上下文继续，保留此前成果版本 |

页面上不增加“请先理解这些状态”的常驻说明。解释放在异常、能力不可用、首次配置和详情中；普通成功路径保持简洁。

### 2.2 信息架构

保持现有沟通、成员、资料／知识、记忆、Runtime、定时入口。聊天工作不新增一个必须先进入的“任务中心”。

| 区域 | 默认内容 | 按需打开 |
| --- | --- | --- |
| 会话目录 | 私聊、群聊、频道；未读、执行中、需要处理的轻量标记 | 查找会话、历史搜索；本轮不建设跨模块全文搜索引擎 |
| 会话头 | 对象／成员、当前回复对象；执行入口摘要 | 参与者、会话资料、运行详情、临时 Runtime 选择 |
| 消息区 | 人的消息、角色公开进度、工具摘要、提问／审批、答案和成果 | 整轮过程、工具明细、来源、原运行信息 |
| 输入区 | 一个输入框、资料入口、发送；活动期间提供停止和后续处理方式 | 补充当前／排下一轮；高级上下文与本轮配置 |
| 成果预览 | 点击文件、引用、代码改动后显示 | 宽屏侧栏，窄屏全屏 Sheet；关闭后回原阅读位置 |

会话目录的“需要处理”必须来自仍有效的请求；打开页面或展开卡片不等于完成处理。完成通知只在有新交付时出现，后台工具进度不逐条打扰人。

### 2.3 私聊、群聊和频道

| 场景 | 谁会回应 | 执行中补充／停止的对象 | 资源规则 |
| --- | --- | --- | --- |
| 角色私聊 | 当前角色默认回应；尚无 Runtime 时保存消息并提示未开始 | 当前角色的这轮工作 | 对应角色私有资源＋本会话明确提供的资料，按现有授权解析 |
| 群聊 | 未指定角色时只是群消息；通过回复对象或明确 @ 指定一位角色才启动 | 明确指向角色与原运行，不把一条文字广播给全部角色 | 当前会话共享资料；不自动注入角色私库 |
| 频道 | 默认用于发布与讨论；显式请求某位角色处理才启动 | 同上，操作留在原请求附近 | 频道共享资源；频道可见性不自动扩大执行权限 |

首版一次新派发选择一位角色。可以先请研究员完成，再明确请写作者接手；不自动唤醒所有成员。@ 仅在被解析并展示为明确执行对象时具有派发语义，引用中的 @ 和普通文本不触发运行。

多角色结果按各自运行归属显示，不能把两个角色的工具拼到同一个折叠块。第一版继续尊重宿主当前串行限制，排队原因显示为“等待执行入口”；不以界面能显示多个角色来宣称底层已并发。

### 2.4 执行中再次发送

这是需要固定规则的产品行为，不能每一版变化：

- 当前角色正在工作且本轮报告支持补充：发送默认“补充当前”，输入区可改为“排下一轮”；记住用户偏好，始终显示这次发送方式。
- 执行端不支持补充：提供“排下一轮”，能力解释放在方式选择中；不先伪装成补充，失败后自动新开运行。
- 补充收到 `accepted` 才标记已接收。`rejected` 保留文字，可明确改排下一轮；`unknown` 留待核对，不自动重发。
- 排队项是用户已提交的工作，在当前会话可见、可取消；取消排队保留消息记录，状态标为取消处理。修改采用移除后重新提交，不静默改动已保存要求。
- 正常完成且交付已保存后按顺序开始下一项。停止、失败、权限失效、原运行不明时暂停同一工作序列，用户明确开始后才继续；另一个独立会话不被无条件永久锁住。
- 提问／审批使用自己的回答控件；输入框仍可写草稿和排下一轮。普通“好的”不被系统自行解释为某个工具的授权。

快捷键采用 Enter 发送、Shift+Enter 换行；中文输入法组合期间 Enter 不发送。停止使用可见按钮；避免把编辑文字时的 Escape 偷换成取消任务。快捷键设置可在后续增加，不阻塞首版。

### 2.5 工作过程、结束与回看

一轮显示分成四类：**活动过程、持续可见的交付、待处理事项、运行状态**。最终回答不是“最后一条 assistant 文本”的别名。

- 活动过程：公开进度、工具及可展示的原生状态；按事件顺序排列。仅相邻同类工具可以聚合，不能跨一段进度说明重排。
- 交付：明确的最终／阶段成果与文件；留在折叠区域之外。不能因为成果后还有一个工具调用，就把已交付内容当成过程藏掉。
- 待处理事项：仍有效的问题和审批保持可发现；同一请求只出现一个可操作副本。折叠过程不能隐藏唯一的响应入口。
- 状态：回答开始、完成、失败、停止、结果未知分别表达。用时来自服务器记录；断线期间保留最近已知时间与核对状态，不用假计时证明仍在运行。

普通最终回答开始时允许收起活动；没有活动则不显示空折叠入口。用户展开优先，整轮、工具组、单次详情各自记忆开合。停止／失败保留部分输出；无最终答案不补造一个成功结论。复制只复制所选回答正文；引用进入同一输入框。

用户向上阅读时不被流式输出拉到底，显示“回到最新”；查看附件后恢复锚点。加载更早历史保留位置。折叠偏好与草稿先按当前用户／设备／会话保存，不承诺跨设备同步；真实工作、已提交队列与请求状态必须来自服务端。

### 2.6 审批、提问与外部登录

审批来自执行端实际请求，展示操作、对象、范围和可选决定；不得为了演示而给普通保存额外加一道审批。原生未提供的“永远允许”不能自创。拒绝一项操作后，由原生执行端决定继续、改用其他合法方式或结束。

用户选定后经历“提交中 → 决定送达／结果待确认”；只有后续工具事件可证明实际操作结果。过期、撤销、终态后的请求只读。旧页面点击过期请求由服务端拒绝，重新返回当前状态。

澄清问题用选项和自由输入，不套授权语义；阻塞与非阻塞由请求契约区分。登录／外部授权只打开真实请求提供的链接，完成后核对执行端状态；不收集、复制原生登录凭据。暂不支持的请求类型明确提示并保持原工作状态，不能以默认允许或默认填空绕过。

### 2.7 资料、记忆、工作区与成果

资料选择沿已有个人、角色私有、会话共享边界；“附到本条消息”与“共享到整个群”分别明确操作。群内文件上传默认仅归当前会话，不自动复制进每位角色私库。

首版提供资料选择和常用文件的上传／预览／下载。文件大小、类型和解析支持以实际接入能力展示；Markdown、文本、图片先接，PDF／Office 可以作为文件交付，但只有解析器实际成功才显示可检索。上传失败保留草稿，未完成文件不能被标记为模型已读。

成果至少记录名称、类型、版本／摘要、来源消息与原运行、访问范围、保存位置和可用状态。远端本地路径不是可下载附件；只有内容已回流或经授权可访问的引用才能展示“打开／下载”。代码工作需能查看真实变更摘要／diff；首版不增加完整 IDE、Git worktree、PR 审核或自动提交功能。

工作区使用执行端公开契约中已授权的工作目录或会话。不能把用户在浏览器填的任意本地路径当成设备授权；协议尚不支持选择时显示现有目录与限制。模型、推理、权限、原生 Skills 等继续由原生端管理并按事实只读展示，不用“聊天配置”越权改写。

聊天中的“整理为记忆”“加入知识资料”是明确动作：先显示内容、来源和目标范围，用户可修改再保存。失败独立重试该保存，不重跑原工作。默认不把全量日志和每次答案自动变成长久记忆。

### 2.8 连续工作、换 Runtime 和人工交接

同一角色在同一会话内可以延续原生 session，但需要执行端支持且身份、Runtime、工作目录和授权范围兼容。失去 session 时，清楚说明使用已保存聊天与交接材料开启新 session；不能称为无损恢复。

换 Runtime 只发生在任务边界。切换后使用角色当前设定、授权资料、必要聊天和已回流成果；执行端未回流的文件、私有记忆、登录和 Skills 不会自动迁移。

人工交接入口放在答案／成果菜单：“请另一位成员继续”。用户选接收角色，检查将带过去的目标、成果、依据、未完成事项及资源范围；确认发送后形成新请求并引用原工作。原运行保留，原角色不会被改名成新角色。双方不共享的资料先明确选择可分享范围，不能在交接摘要中泄漏私库。

定时工作继续使用现有日历与安排页。每一期进入同一套运行展示、审批和成果链路；需要人时标记当前期，不能把暂停单期、停止当前运行、停用未来安排混成一个按钮。五个现有股票安排及业务规则保持连续，后端升级不能再派发同一期。

## 5. 技术结构与职责

沿用 Next.js／React／assistant-ui、NestJS＋Fastify、TypeORM＋PostgreSQL 和独立模块。新增的是薄协调与投影，不另做模型推理循环。

```text
浏览器：输入、阅读、明确操作；只持有 UI 状态
  │ HTTP 操作 + SSE 事件／快照
hutian Web BFF：会话授权、响应裁剪、流转发
  │
hutian API + durable worker：业务请求、排队、资源授权、交付引用、恢复
  ├─ Matrix Agents Chat：房间、成员、消息、回复、历史
  │    └─ 可选执行宿主：原 job／receipt、Dock 连接、事件缓存、请求代理
  │          └─ Harness Dock → 已授权设备 → 原生 Harness／工具／文件
  ├─ 资料接入 → AnythingLLM＋已保存原文／附件
  └─ 记忆接入 → Memory Access 协议 → Hindsight／Mem0 OSS／受管笔记
```

独立模块继续可以独立使用。宿主能力从当前 example 逐步提取为可选适配层，由宿主自己持有原执行回执，不把 hutian 的角色、工作台和安排概念写入通信核心。既有 CLI 和网页示例可保留消费同一适配层。

### 5.1 唯一事实来源

| 信息 | 权威保存者 | 其他模块保存什么 |
| --- | --- | --- |
| 用户、空间、角色、调用资格、资源授权 | hutian 业务库 | 必要的已校验身份和版本引用 |
| 房间、成员、聊天正文、回复关系 | Matrix | 消息 ID、投递状态、可重建阅读投影 |
| 原运行、原生 session、工具与运行终态 | Dock／原生 Harness | 宿主原回执与事件来源，hutian 保存引用和最近确认快照 |
| 用户已提交待办顺序、人工交接、每期业务要求 | hutian 业务库 | DBOS 保存协调执行进度，不代替业务定义 |
| 审批原请求及原生接收结果 | 执行端／Dock，宿主保留转交凭据 | hutian 保存谁提交了哪个决定及送达状态，不自己宣布工具成功 |
| 原文、成果文件、资料版本 | 现有资料／附件存储 | 业务归属、内容 hash、来源与授权引用 |
| 长期记忆 | 所选记忆后端与 Memory Access 的来源档案／原操作引用 | 来源、范围及保存操作引用；不能作为唯一工作账本 |

运行事件缓存是可审计的原事件副本，不是另一套能自行判定成功的执行引擎；缓存缺失必须显示缺失并按源核对。

### 5.2 身份与关联模型

以下是**拟新增／补齐的契约**，名称不是对现有接口的宣称：

| 对象 | 关键字段 | 约束 |
| --- | --- | --- |
| `ChatRequest` | id、workspaceId、requestedBy、runAs、roomId、sourceEventId、roleId／agentId、connectionRefs、mode、predecessorId、requestVersion | 业务“处理这条消息”的身份；同一消息不同角色是不同请求；相同提交不产生第二请求 |
| `ExecutionLink` | requestId、hostJobRef、dockRunId、providerTurnId、nativeSessionRef、runtimeSnapshot、receiptRef | 保存原对应关系；更换默认 Runtime 不重定向旧运行；原生敏感标识和凭据不下发浏览器 |
| `ChatOperation` | operationId、requestId、kind、actor、payloadHash、expectedRevision、deliveryState | 补充、停止、决定、答案等独立操作；重试同一 ID 返回原结果，不能换 ID 重放未知操作 |
| `Interaction` | requestId、nativeRequestId、kind、schema／decisions、blocking、revision、expiresAt?、status | options／form／url／question 等按能力映射；无过期时间不编造 TTL，终态与原生 resolved 均使其失效 |
| `RunEventProjection` | runId、sequence、kind、itemId?、phase?、payload、sourceVersion、receivedAt | 追加并去重，保持原序；明确未识别类型与缺口；不持久保存每次 React 渲染 |
| `DeliveryRef` | id、requestId、messageId、name、mime、size、hash、version、storageRef、scope、status | 回流成功才 available；外部路径引用与托管文件区分 |
| `ContinuationRef` | roleId、roomId、connectionRef、nodeId、provider、sessionKey、scopeVersion、lastRunId | 角色／会话隔离；权限或环境不兼容时停止复用原 session |

`ChatRequest`、操作意图及成果归属放 hutian 的本地 PostgreSQL，显式 migration；表与查询带空间／拥有者字段和复合关联，沿第 6 段上下文。既有 `scheduled_runs` 关联同一个请求，不复制一份 native run 生命周期。宿主 job／receipt 继续在其私有存储；事件投影与交互转交记录属于可选宿主，提供可替换存储接口，先沿现有本机文件方式原子写入、受限权限和单写者管理，不为通信核心强加业务数据库。

在接收请求时冻结用户选择的角色、Runtime、资料引用和要求；排队真正开始时再检查当前权限，并生成上下文快照。队列可纳入同一会话前序工作的已确认结果，但记录实际纳入的消息／资源版本与边界。默认绑定、资料版本或资格发生变化不能无提示换目标执行：保持所选版本可用就按原版本，无法继续则转待处理。

### 5.3 状态必须分层

| 层 | 建议状态 | 关键含义 |
| --- | --- | --- |
| 消息投递 | sending／sent／send_unknown／failed | Matrix 收到不等于原生已开始；超时先核对同一事务 |
| 业务请求 | accepted／queued／preparing／dispatched／delivery_pending／done／blocked／cancelled | done 表示本次交付流程处理完成，可包含明确失败交付；不代替原生终态 |
| 原运行 | running／completed／cancelled／failed／unknown | 直接归一 Dock 状态；Codex interrupted 映射 cancelled，保留原值 |
| 内容阶段 | commentary／partial_answer／final_answer／unclassified | phase 决定内容位置，不能决定整个运行结束 |
| 待决项 | pending／submitting／delivered／delivery_unknown／resolved／expired | 决定送达与工具效果分开；多个请求各有状态 |
| 连接 | connected／reconnecting／unavailable | 断线不把 running 改为 failed 或 cancelled |
| 展示 | auto／expanded／collapsed；工具详情独立 | 用户偏好，不写进运行事实 |

状态文本由“当前原运行＋待决项＋连接”组合投影，避免多处各写一个 running 布尔值。收到 final 文本可以进入“回答中”；只有确认原运行终态才能显示完整结束操作。收到终态后缺少最终文本或附件时显示“执行已结束，交付待核对”，不得回退重跑执行。

### 5.4 四条端到端链路

**发送新工作：** 浏览器带稳定 clientMessageId 提交 → BFF 检查身份和成员 → Matrix 按事务 ID 保存消息 → 业务接受请求并冻结选择 → worker 校验授权与入口 → 宿主持久保存 job／预分配 runId／原连接信息 → Dock 派发 → 原事件和回执返回 → 交付保存 → Matrix 使用稳定回复事务 ID 发布最终消息 → 页面把临时运行视图与正式回复关联起来。

初次 Runtime 离线：消息保留，执行显示未开始，用户稍后明确重试；不默认在数小时后突然开始。已经明确接受的排队项遇到短暂入口占用可以等待；遇离线或超出配置的启动有效期转 blocked，保留顺序并提示。定时任务继续使用自身的启动窗口与 missed 规则。

**补充／停止／审批：** 浏览器提交带 operationId 的操作 → 重新校验调用者、run、请求修订和可用决定 → 保存操作意图 → 交给持有原连接的宿主 → Dock／原生接收结果 → 更新送达状态 → 等待后续事件。控制通道优先服务活动运行，不能排在本轮结束之后；普通断开页面不会发送停止。

**最终交付：** 保留原生终态 → 提取明确 final 内容／真实工具成果 → 收集并校验附件 → 保存交付引用 → 发送 Matrix 最终回复。发布失败只重试发布，附件失败只重试收集／保存；已经完成的模型工作不会重跑。无 final 但确有附件可作为文件交付，并说明缺少文本总结；无任何可确认成果显示具体情况，不造默认成功文案。

**返回聊天／服务重启：** 先读消息与已知运行快照 → 订阅 after cursor → 宿主按原 receipt 查询 getExecution／events／必要 reconcile → 合并终态和后续事件。没有原回执或查询不支持时保留 unknown；不会创建一个新 run 来“修复”旧 run。

### 5.5 事件、流式展示与历史

建议 Web 提供 SSE，操作仍走普通 HTTP。消息历史来自 Matrix；运行活动来自宿主。BFF 组装一份带来源的会话快照，不把 token 增量逐条发成 Matrix 聊天消息。

- Dock 的 run sequence 用于单运行去重；Matrix 事件有自己的游标，不伪装成全局同一个序列。BFF 的订阅 cursor 是包含两者位置的服务端令牌。
- 先取得快照水位，再补水位之后的事件；重连从确认 cursor 继续。乱序按原 sequence 排列，不按浏览器接收时间拼文字。
- 增量绑定 item／message ID；最终文本替换该消息的累计内容，不再追加一遍。正式 Matrix 回复出现后，按 request／run 关联替换占位展示，防止两份答案。
- `historyTruncated`／`detailsExpired` 出现时标记部分过程缺失，展示可确认的快照／成果；不拼一个看似完整的日志。历史恢复不再次触发工具。
- 相邻文本增量可以在 UI 层小批合并；交互请求、终态和错误立即推送。服务端压力大时优先保留原事件来源与关键状态，不能丢审批或终态。
- 活跃页 SSE 失效时退回带 cursor 的受限轮询；后台页降低观察频率。关闭浏览器不关闭宿主执行。当前一次只读最近 100 条需补 Matrix 历史分页，避免将固定窗口当完整历史。
- 公开 commentary 可以展示；原生私有推理和日志中的秘密不因技术上收到就进入用户消息。工具输入输出做必要裁剪，原生不提供的阶段标记保持未分类，不靠措辞猜测 final。

### 5.6 宿主与能力适配

将当前“每个请求启动一个等待最终 stdout 的 CLI 子进程”逐步替换为**持续宿主中的 Dock Client 适配器**：持有原连接、接收回调、记录事件与交互，并响应控制。保留原 CLI 查询作为兼容恢复入口。连接以授权连接身份归属，一个连接身份由一个宿主 owner 管理；浏览器与 BFF 不另开同身份竞争连接。

首先保持当前串行执行准入，控制操作仍可到达当前运行。后续只有在 Dock 和设备能力确证支持时，才按连接／设备／原生 session 限制放开并发；同一 session 永远不并发写入。持久等待和审批不能占住唯一“控制命令队列”，否则会出现等待审批而审批永远送不进去的死锁。

| 能力 | 当前公开契约 | 产品处理 |
| --- | --- | --- |
| 补充 | steer 的 accepted／rejected／unknown，steering available 回调 | 本轮 available 才启用；能力缺报按不可用，不按 provider 名称猜 |
| 停止 | cancel requested 与可选状态 | 点击后保持请求中，等原终态；停止与完成竞态以原运行最终证据为准 |
| 查原结果／事件 | getExecution、events(after)、reconcile 与过期标志 | 恢复观察，不盲目重新 execute |
| 交互 | permission options／form／url，permissionDelivered | 明确映射授权／提问；缺独立提问／request-resolved 元数据时窄扩契约，不能只凭显示标题判断 |
| 连续会话 | sessionResume、sessionKey／resumeSessionId／previousRunId | 绑定经过验证的会话范围；当前宿主尚未完整使用这些参数，作为 C 批次交付 |
| 最终文本 | exactFinalAnswer 与 provider 事件 | 缺能力时显示受限，不从普通最后一行猜最终成果 |

Dock 的浏览器能力目前契约标为 unverified，桌面工具有独立状态；不能因为选了 Codex 就在 hutian 宣称所有浏览器／桌面操作可用。权限策略仍由原生执行环境决定。

## 6. 接口设计

以下为拟提供给 Web 的 HTTP 形态，实际落地沿现有 Server Actions／BFF 复用；现有 Matrix `/api/messages`、`/api/agent`、`/api/agent/resume` 保持兼容。内部宿主接口同步增加对应的事件与控制能力，不把浏览器直连设备作为捷径。

| 接口 | 输入核心字段 | 返回与语义 |
| --- | --- | --- |
| `POST /api/chat/rooms/:roomId/messages` | clientMessageId、text／attachments、replyTo?、targetRole?、mode | eventId、requestId?、messageState、requestState；允许消息已收而执行未开始 |
| `GET /api/chat/rooms/:roomId/state` | before? | 消息页、运行投影、有效交互、队列、cursor；权限裁剪 |
| `GET /api/chat/rooms/:roomId/events` | after | SSE 的消息变化／运行事件／请求变化／缺口与水位 |
| `POST /api/chat/requests/:id/steer` | operationId、text／资料引用、expectedRunId | 操作记录与 pending／accepted／rejected／unknown；明确对象 |
| `POST /api/chat/requests/:id/stop` | operationId、expectedRunId | 已接受停止意图，不等于 cancelled |
| `POST /api/chat/requests/:id/interactions/:key/respond` | operationId、expectedRevision、原生允许的 response | 意图保存与送达状态；过期／冲突返回最新请求 |
| `POST /api/chat/requests/:id/reconcile` | 原请求身份 | 查询原运行，不派发新运行 |
| `POST /api/chat/requests/:id/continue` | operationId、新要求、sourceRefs | 明确创建新请求，可复用合法 session；不是恢复旧失败运行 |
| `POST /api/chat/queue/:id/cancel` 或 `/start` | operationId、expectedRevision | 原子改变待办状态；已派发不能再当作队列取消 |
| `POST /api/chat/requests/:id/handoff` | operationId、targetRole、目的、选定引用／范围 | 新请求与原请求关联；仅显式人工交接 |
| `GET /api/chat/deliveries/:id` | 当前身份 | 有权访问的预览／内容；路径不可直接从用户输入拼接 |

身份从服务端上下文取得，用户不能用 body 中的 userId／workspaceId 自选权限。操作使用预期版本避免陈旧页面决策：同 operationId 同 payload 返回原记录；同 ID 不同内容返回 409；请求失效返回最新状态和明确错误。HTTP 202 只表示已接收处理，不显示为原生已完成。

新增能力是窄增量：operation 送达查询、可恢复交互标识、必要 phase 类型和事件投影。不会为了前端统一把 unsupported 改成“模拟成功”。

## 7. DBOS、排队与恢复的决定

**推荐：在 C 批次小范围接入 DBOS；无需把旧 hutian 的整套 DBOS 工作流迁过来，也不新增 Redis／BullMQ 与它重复承担同一工作。** A／B 先完成真实事件和控制闭环，C 才把已明确的业务步骤放入 durable worker。首个可靠范围为“接受请求 → 派发／核对原运行 → 保存／发布交付”。

依据：官方 [Workflows](https://docs.dbos.dev/typescript/tutorials/workflow-tutorial) 说明工作流检查点和固定 workflow ID；[Steps](https://docs.dbos.dev/typescript/tutorials/step-tutorial) 区分外部操作与重试；[Queues](https://docs.dbos.dev/typescript/tutorials/queue-tutorial) 提供并发控制。这里选择它来减少自写恢复机制；**对外部 Harness、文件和第三方工具的副作用，仍需原系统的幂等与核对，不能由 DBOS 的完成记录推导为 exactly-once。**

| 候选 | 适用性 | 本稿选择 |
| --- | --- | --- |
| 继续扩当前 timer＋租约＋文件恢复 | 短期依赖最少，但等待、队列、重启恢复会逐步各写一套 | 保留为现状与切换前兼容，不作为长期继续扩建方向 |
| DBOS＋现有 PostgreSQL | 和现有技术栈及旧版窄机制接近，覆盖持久等待与协调恢复 | 推荐，单独兼容验证后小范围接入 |
| 另加 Redis／BullMQ | 适合纯后台 job，仍需自行处理多步等待与原运行关联 | 当前无明确收益，不同时引入 |
| Temporal 等独立工作流平台 | 可处理更复杂规模和运维场景 | 本机 MVP 暂无足够收益，不增加部署面 |

DBOS 放在服务端 worker，不放浏览器、Next 页面生命周期或原生推理循环中。复用本地 Docker PostgreSQL，使用适当独立 schema／最小权限账号，凭据保留私有配置；版本按实施时实际 Node／数据库／SDK 兼容结果固定。旧项目锁定的 `4.27.6` 与当前官方文档不能直接混用 API；只移植“持久等待、同身份核对、交付再试”的窄原则。

业务表保存用户可见队列顺序与暂停原因；DBOS 管理同一请求的唤醒和恢复，不再建一套并行 dispatch timer 去执行同一请求。接收业务请求与确保启动 workflow 之间使用事务内 outbox／可扫描的未启动意图，稳定 workflow ID 以 workspace＋requestId 派生；恢复扫描只补启动同一个协调工作流，不重建业务请求。原 schedule 的 tick 仍可计算到期实例，实际派发统一委托 worker，移除旧的重复派发责任。

**恢复必须遵守的边界：**

1. 先持久保存派发意图和原身份，再调用外部系统。网络超时不能证明未执行；Dock 查询无法确认时停在 unknown，不用新 runId 补发。
2. Matrix 消息／最终回复复用稳定事务 ID；结果已存但发布失败只再发原结果。
3. 补充和授权这类外部控制若没有明确原生幂等支持，unknown 后先核对，不由 DBOS 默认重试重新发送。只对已知可重试步骤开启重试。
4. 等待原生结果采用可恢复信号＋定期核对，不把长时间连接等待包装成一个可任意重跑的 execute step。完成信号丢失时查询原 run，而不是再启动。
5. worker 租约和 owner generation 防止两个宿主同时派发；原 owner 失联时先核对原生工作，新 owner 不凭锁过期就判断执行从未开始。
6. DBOS 自身中断、停止或超时不等于原生工作被停止。用户停止必须走 Dock；后台协调仍保留核对与交付职责。

### 7.1 关键故障处理

| 故障／竞态 | 用户看到 | 后台处理 |
| --- | --- | --- |
| 消息保存成功、派发失败 | 消息已发送，工作未开始 | 复用原消息建／查同一请求，不发重复用户消息 |
| 派发已发生，HTTP 超时 | 开始结果待确认 | 用原 run／receipt 核对，不自动新派发 |
| 网页刷新或退出 | 再回来接原工作 | 执行不归浏览器所有；读快照并补事件 |
| 宿主重启／设备离线 | 最近状态＋待核对 | Dock 是否能继续依能力与实际证据，不承诺任意故障后不中断 |
| 停止与完成同时到达 | 显示最终确认状态 | 若已完成就完成，不把较晚的停止意图覆盖终态 |
| 决定已保存但送达未知 | 审批结果待确认 | 阻止冲突决定与无依据重发；查同一请求 |
| 原生结束后才收到旧审批 | 历史只读 | 按 run／request revision 拒绝，不能让旧请求重新生效 |
| 事件重复、断档、历史过期 | 内容不重复；缺失明确标记 | 按来源去重／补快照，终态不因晚到进度倒退 |
| 附件回流失败 | 答案保留，文件待取回 | 单独补取原成果，文件 hash 校验；不重跑模型 |
| 结果已保存、Matrix 暂不可用 | 工作已结束，回复待同步 | 用原回复事务再交付；正常队列待交付保存确认后推进 |
| 资格或资源被撤销 | 后续派发／读取阻止 | 已进入原生端的内容无法“撤回未看过”；有权时发停止并说明确认状态 |
| 重启后发现多期定时记录 | 保留既有每期历史 | 按 schedule occurrence 的唯一身份继续，不重新批量发送五个任务 |

## 8. 权限、数据与可运维性

每次发送、派发、补充、停止、审批、下载和交接，都核对当前身份、空间、会话成员关系、目标角色与连接归属。首版当前用户拥有自己发起工作的控制资格；群聊中“能看见”不等于“能替别人批准”。后续多人产品需显式授予执行控制／审批权，不能从同空间成员身份推导。

原模型登录和设备凭据留在执行端；Matrix／Dock／记忆／知识服务凭据留在可信服务端，不进入 prompt、事件 SSE 或可下载日志。工具输出、Markdown、HTML 文件按内容类型处理；HTML 不在主应用同源直接执行，预览使用隔离上下文。外链、文件下载、路径和表单都按当前原请求及范围处理。

原生 session 会保留此前上下文；资源权限缩小时，禁止继续复用可能含已撤销内容的 session，开启合法的新上下文。当前人读历史与下一次 Agent 读材料分别检查，不能简单复用浏览器拿到的整段对话作为模型输入。

日志只记录 requestId／runId／operationId、来源模块、时间、状态和错误分类，秘密脱敏。诊断页按需查看最近连接、原回执是否存在、等待原因和最近核对时间。关注从发送到接收、首次真实活动、决定送达、原生结束到交付可见的耗时，避免只计一个总耗时误判瓶颈。当前用户已暂缓模型连接延迟排查，本方案不另起该排查。

保留业务成果和正式消息；运行过程缓存允许按明确保留期压缩／到期清理，UI 标记细节过期。文件／记录删除沿现有保留历史语义，不能为了清空界面而删原执行证据。备份覆盖业务库、私有宿主 job／receipt、原文附件与必要模块备份；浏览器缓存不作为恢复来源。

部署仍以本机单人工作台为范围。Web、API／worker、通信宿主、PostgreSQL 和现有资源服务有明确启动与健康检查；控制宿主只对可信服务开放。多人公网认证、跨空间真实验证和高可用集群另列后续，不由这次接口加字段就宣称完成。

## 9. 实施批次、文件落点与验收

每批都是可演示的完整路径。估算是单一实现流的有效开发日范围，含必要编译和人工核对，不含未知上游故障／发布审批；A–E 合计约 12–19 个开发日，用于范围判断而非已承诺日期。本周先争取 A＋B 的真实单角色闭环，C–E 分批完成，不为赶日期省略后台真实性。

| 批次 | 可使用成果 | 主要落点 | 预计／依赖 | 验收停点 |
| --- | --- | --- | --- | --- |
| A 真实执行与展示 | 同一聊天自然执行；公开进度、工具、答案、整轮收起；历史可回看 | Matrix 可选宿主的事件适配；Web communications／assistant-ui；Dock phase 窄补齐 | 3–4 日；依现有 Dock | 一次真实只读研究工作，过程与最终答案按原事件显示；刷新不重复；手动展开不被覆盖 |
| B 人在过程中介入 | 补充、停止、提问、审批和故障确认，支持能力降级 | 宿主控制通道、交互投影；Web action／卡片；旧 native-interaction 按需复用 | 3–5 日；依 A | 实际受限操作允许／拒绝、真实补充与停止分别收到回执；不支持的 Runtime 不显示假能力 |
| C 连续工作与可靠后台 | 持久排队、合法 session 延续、离开／重启恢复、既有定时复用 | API 请求／操作表与 migration、DBOS worker、宿主 owner／恢复；schedule 派发委托 | 3–5 日；依 B | 关闭网页仍交付；重启后核对原 run；排队停止后暂停；五个安排原标识与周期保留 |
| D 资料与真实成果 | 文件进出、预览／下载／来源、真实代码 diff、保存资料／记忆 | 现有资源与 report-attachments 接入、DeliveryRef、预览 primitive | 2–3 日；依 A／C | 一份真实文件回流、重复读取不依赖原设备在线；共享范围与来源正确；保存失败不重跑任务 |
| E 群聊与人工交接 | 指定角色回应、操作归属清晰、选成果转交与新执行端接替 | role-chat、资源范围、交接接口、群聊会话投影 | 1–2 日；依 C／D | 两位角色先后完成研究→整理；接收者只获准材料；原作者、运行和成果关联保留 |

涉及源码的主要位置：

- hutian：`apps/web/src/components/communications.tsx`、`components/assistant-ui/`、`lib/communication-actions.ts`、`lib/communications.ts`、`lib/role-chat.ts`、`lib/resource-scopes.ts`、`lib/report-attachments.ts`；API 新协调服务／worker 和数据库 migration；`packages/contracts` 增量契约。
- Matrix：从 `examples/dock-host.ts`、`examples/host-worker.ts`、`examples/web/server.ts` 提取／扩展可选宿主层；保留原消息、job 与 receipt 兼容，通信核心不新增 hutian 业务模型。
- Dock：优先使用 `packages/client` 与 `packages/protocol/src/execution.ts`；只有确认缺失的 phase／交互元数据在 `packages/drivers` 与协议中窄补齐，不重写 driver。
- 旧 hutian：参考 `runtime-permissions.tsx`、`runtime-native-interaction.tsx` 的状态与表单，`platform/dbos/durable-world.ts` 的窄恢复机制；原设计 primitive 按当前 DESIGN 复用。

不新增测试框架、fixture 或自动化测试矩阵。按用户约定做必要 typecheck／build 和最短真实使用检查，记录实际 run／消息／交付引用。核心人工验收覆盖以下工作情境，不能只凭原型通过：

1. **正常与完成：** 发送一次真实工作，观察真实工具与 final；最终回答外置，过程独立折叠，历史与原运行一致。
2. **交互与停止：** 审批允许／拒绝、提问回答、执行中补充；点击并非成功，核对送达和实际后续。停止保留输出，队列不擅自继续。
3. **断开与重复：** 刷新网页、短断连接、宿主重启；同消息／同请求无第二次 execute，未知保持未知，结果发布只一次。
4. **资料与交接：** 上传／引用、成果回流、打开来源；私库不因群聊或交接扩大；角色换 Runtime 后使用已回流材料完成下一轮。
5. **旧数据与安排：** 老消息、角色、记忆、知识和原日报仍可读；已有五个安排及已生成期次不重复派发，控制入口能区分本期和未来计划。

### 9.1 切换与回退

采用增量 schema 与显式 migration，先备份业务库和私有宿主记录。新事件展示可按会话开关启用；旧历史没有活动数据时仅展示原文本，不补造工具记录。旧 job／receipt 继续沿旧读取器查询；只有新接受请求进入新宿主路径，不把正在执行的旧工作迁到新 run。

DBOS 与旧派发器切换按请求所有权完成：同一个请求只能有一个派发 owner。先停止旧派发领取、核对在途实例，再启用新 owner；回退同样先排空／核对，不直接重启两个派发器。新表保留可读，回退不删除原消息或执行历史。五个定时安排迁移仅改变协调实现，不重新创建计划与历史。

每批最新完成内容保持未提交供查看 diff；明确进入下一批时按既有规则先单独本地提交上一批。公开发布、推送和 X 分享仍按具体授权；本次方案没有执行这些动作。

### 9.2 独立模块与开源交付边界

2026-11-15 补充，回应用户“还有需要单独拆子项目可开源的部分么”。以下是建议，不代表已经采用拆仓或授权公开发布。

**本轮独立源码项目为 Memory Access；聊天工作流作为 Matrix Agents Chat 的可选宿主增量和 hutian-world 的应用功能交付。Dock 沿现有 SDK 使用，聊天 UI 保留为后续提包候选。** 独立交付可以发生在现有仓库中，不要求每个内部模块新增仓库、服务和数据库。

| 部分 | 独立使用者与可交付价值 | 代码／仓库安排 | 时机 |
| --- | --- | --- | --- |
| Harness Dock | 其他应用调用已授权电脑上的 Harness，接收事件、原生交互与结果 | 继续现有独立仓库；通用客户端的事件订阅、控制和结果操作放其公开 SDK，避免再造一层同职责执行系统 | 随 A／B／C 的真实需求补齐 |
| Matrix Agents Chat 可选执行宿主 | 外部产品无需 hutian 的角色库和业务库，也能让指定 Agent 在 Matrix 房间执行、展示活动、批准、停止并回复原消息 | 从现有 `examples/dock-host.ts`／`host-worker.ts` 提取正式可选模块，先同仓提供独立入口或包；核心通信 SDK 继续不依赖 Dock、DBOS 或 hutian-world | 本轮最有价值的新增独立交付，随 A／B 完成 |

| 聊天运行 UI 适配 | 其他 React 应用将已确认的运行事件、工具、交互和终态接入 assistant-ui，复用整轮活动与交付分层 | 先在现有 Web 中稳定适配契约；当另一个实际宿主应用复用时提取可安装包，仓库位置再按维护需要决定 | 后置候选，不作为 A／B 前置，也不新建通用聊天框架 |

其中，**Matrix 可选宿主与 Dock 的职责必须继续分开**：Matrix 特有的 room／event／reply 关联留在宿主；通用设备连接、原运行查询和原生控制留在 Dock；hutian 的角色、空间、授权、业务队列和定时要求留在 hutian-world。可选宿主接收调用方上下文，不自行创建 hutian 身份、资源或另一套排队业务。

#### 记忆接入层独立交付的范围

已改为一套与记忆引擎分开的版本化协议。调用方只使用授权资源 ID；操作员映射连接与 namespace，后端可以是托管服务或自部署。Hindsight 负责自己的存储、提取和归纳，Mem0 使用自己的 native memory 和向量存储，受管笔记只支持原文保存和词项检索；网关不冒充统一记忆引擎。

基础操作为能力发现、明确 infer／verbatim 写入、检索、原文来源、原操作观察及声明范围的删除。MCP 是调用传输，HTTP v2 和 CLI 消费同一协议。模型选择、资源迁移、跨后端混排和高级 reflect 不被静默统一。详情以 [协议](../../memory-access/PROTOCOL.md) 和 [实际交付](../../memory-access/DELIVERY.md) 为准。

已有 Hindsight v1 调用、资源、bank 与凭据保留。Hutian 新接入使用 v2；独立项目可以不安装 Hindsight，从受管笔记开始。独立交付不宣称其他产品没有权限或 MCP，也不自动新增公开仓库、发布包或改远端可见性。

#### 可选宿主与 UI 的独立验收

可选宿主的独立演示是：干净安装 Matrix Agents Chat 与自己的 Dock 连接，在本机示例网页发一项真实工作，观察真实工具活动、处理一项原生请求、停止或完成，并确认回复指向原消息；全过程不依赖 hutian-world 的数据库。该演示证明通信与执行接入的可复用性，不证明任意故障后的自动恢复或多人公网授权。

UI 适配的提取条件是：真实事件模型稳定、另一应用存在明确复用需求、调用方可以注入状态／动作／主题／权限，且不依赖 Hutian 的路由、角色和数据库。通用消息、输入、滚动与工具渲染继续复用 [assistant-ui 的 ExternalStoreRuntime](https://www.assistant-ui.com/docs/runtimes/custom/external-store)；只发布有实际差异的事件适配与运行展示。若缺口适合 upstream，优先考虑贡献，避免维护整个 UI 的重复副本。

#### 当前保留在 hutian-world 的内容

角色资料与执行绑定、会话授权与资源选择、人工交接、业务排队、周期安排与 DBOS 业务工作流、成果业务归属和验收继续在 hutian-world。知识接入与成果预览目前优先复用现有服务／组件，还没有足够独立使用收益来支撑新增项目。将来存在第二个真实消费场景时再评估；“成果服务”“知识网关”“通用调度器”均不因本稿命名就进入新建范围。

独立开源成果按现有仓库增强、可安装模块和候选新仓分别记录。新建公开仓库、切换已有私有仓库可见性、发布 npm／PyPI／Release 或向上游提交 Issue／PR，继续按具体动作授权；本文只补充拆分建议。

## 11. 输入与执行配置补充核对（2026-11-15）

历史方案：本节保留当时的补齐依据；输入区执行配置、会话覆盖及草稿扩展已由 §12.1 最终裁决取代，当前实现与验收以该节及当日验收最新补充为准。

### 已确认的现状与参考

- 新 hutian 的成员执行设置仅保存节点、Harness 和标签。`RoleRuntimeForm` 目前没有模型／推理等级字段；`setRoleRuntime` 在节点与 Harness 相同时直接返回，后续增加配置时必须一起修正比较与版本校验，不能出现点了保存但没有落库。
- 旧 hutian 的 `conversation-runtime-settings.tsx` 已有短模型名、按模型查询支持选项、推理等级、会话覆盖及恢复默认；`conversation-mentions.ts` 和 `CommunicationMentionTrigger` 已有成员标识、中文连续输入触发 `@`、邮箱排除、重名区分和 assistant-ui Mention 组合。按需移植交互与适配，不搬旧 Core 或其客户端队列。
- Dock 的公开 `DeviceExecuteInput` 已支持 `model` 和 `config`；具名 Driver 校验实际模型、effort、serviceTier，并在原生会话应用。当前 Matrix 普通聊天桥接只传了 model，Hutian 派发也未提供完整选择；需要把保存、校验、冻结、桥接、原生应用与回执展示接成一条链。
- 本方案不要求修改 Harness Dock 的协议、Server、Daemon 或具名 Driver。当前聊天桥接使用 `ServerClient.node().request('execute', ...)`，可沿已有契约传入 config。高层便捷接口 `Dock.run()` 当前只暴露 model，不能据此声称整个 SDK 已有同样的便捷配置入口；本次无需改用或扩展该接口。Dock 面板仍只读展示原生状态，配置属于 Hutian 的成员／会话偏好及当次执行请求，不写回设备的全局原生配置。
- 实际只读 Mac 清单包含模型及各自 efforts/serviceTiers；原生 configOptions 也上报当前模型与 reasoning_effort。选项必须按设备和 Harness 读取，不能从 Mac 推断 Windows，更不能用某模型的档位作为所有模型的列表。
- [Multica 成员配置](https://multica.ai/docs/agents-create#runtime-model-and-thinking-level)：先选 Runtime，再选该执行工具支持的模型、thinking level、服务档位；空值跟随 Runtime／CLI 默认，编辑不改变已经开始的运行。[聊天文档](https://multica.ai/docs/chat)将附加上下文放在输入左下 `+`，私聊对象由会话确定。
- Cindy 本轮固定 `5f35635a26c3061a87302894e247d306c83faf8c`：[ChatInput](https://github.com/makecindy/cindy/blob/5f35635a26c3061a87302894e247d306c83faf8c/apps/desktop/src/renderer/components/new-chat/ChatInput.tsx)、[ModelSelector](https://github.com/makecindy/cindy/blob/5f35635a26c3061a87302894e247d306c83faf8c/apps/desktop/src/renderer/components/new-chat/ModelSelector.tsx)。其选择器明确区分设备／来源、模型与 effort，选择应用结果和 UI 选中状态保持一致；不把其整个模型路由、收藏或实时配置体系引入本 MVP。
- [Codex 官方设置](https://learn.chatgpt.com/docs/app/settings)确认执行中跟进可 Steer 或 Queue，默认行为可配置；文档不证明具体按钮位置。输入底栏与单角色发送／停止继续按当前 DESIGN 的窄例外核对，不能宣称所有原生交互已完整复刻。

### 产品行为

1. **私聊**：对象由当前会话确定，不重复放“请谁回复”；默认直接输入并发给该成员。
2. **群聊与频道**：输入 `@` 从当前已加入的成员中选择，在正文呈现可键盘操作、整块删除的 Mention。没有 `@` 是普通消息，不隐式启动全部成员；点名多位时分别形成各自请求，沿各自默认 Runtime，不把多个目标缩成一个设备。邀请仍在成员管理中。
3. **输入框**：上部专注正文与已附材料，底部一行放 `+`、紧凑执行配置摘要和发送／停止。附件、知识、记忆和资源范围详情收入口；已启用的参考来源仍需可见，不能把自动共享的范围藏起来。群聊按明确目标显示配置摘要，多位成员显示各成员默认，点击查看分别使用的设备与配置。
4. **成员默认**：保存 Runtime、模型、推理等级，以及实际支持的服务档位。未设置的字段跟随执行端，不用虚构“默认模型”值覆盖原生设置。
5. **会话临时覆盖**：只影响当前会话的新请求，优先于成员默认；每个字段可以恢复跟随成员。更改 Runtime／模型后重新校验依赖的档位，不能悄悄替换成其他选项。没有能力、离线及读取未知分别表达。
6. **范围与生效时间**：本次明确覆盖 → 成员默认 → Runtime 原生默认；派发时冻结，改变选择不修改在途运行。排队条目保持提交时的选择。权限配置仍按现有产品约定沿执行端规则，不因新增模型／推理选择器改变原生默认权限或授予更大权限。

### 技术接线与验收

- 用同一份原生能力解析和校验逻辑服务成员配置页与输入底栏；保留原生值，中文标签只做展示映射。
- 成员配置采用显式 migration 增加可选执行偏好；旧绑定默认空对象。比较完整配置，沿原版本做并发校验。
- 会话草稿与临时偏好按当前会话、成员与 Runtime 隔离；用户提及成员的身份来自结构化 Mention 标识，不能依赖同名显示文本猜测。输入恢复未完成时阻止发送；失效成员不得静默变成普通消息或换人执行。
- 业务请求保存冻结后的请求模型／config、成员设置版本和能力依据；Matrix host context 严格白名单后透传 Dock，不构造任意原生命令或远程环境变量。不同请求或后台恢复不能混用新偏好。
- 最终核对请求值与执行端确认值，二者不能混为 UI 当前选择。具名 Driver 的实际设置失败必须失败并保留原因，不能展示为已经生效。
- 真实验收覆盖私聊直接输入、群聊 @ 单／多成员及取消、中文与邮箱、键盘选择、草稿恢复、执行中补充／排队／停止；两台设备设置不同模型／effort，核对成员默认、临时覆盖、恢复默认、重载、失效选择及原运行不被修改。原五个股票安排的冻结配置保持不变。

### 12.1 用户反馈后的再评审与最终裁决

真实执行通过后，用户指出聊天框修改 Runtime 在多成员群聊中仍显混乱。当前底栏实际保存的是逐成员会话覆盖，但入口看起来属于整个输入框，使用者需要额外理解“先选哪个成员，再改其执行环境”。功能可执行不代表这项交互已获用户认可。

agentes-chat 的当前源码将电脑、模型与推理配置归于具体 Agent；群聊 Composer 无统一执行配置，私聊顶部提供该 Agent 的快捷入口。其模型快捷操作更新 Agent 默认配置，不是本会话覆盖。来源及范围见 [开发参考补充](../../docs/development-references.md)。

用户随后明确“处理吧，对齐它”。最终按 agentes.chat 的成员归属统一：Runtime、模型与推理等级全部归成员；群聊／频道输入区只保留消息、点名、资料和发送，不再放“多位成员各自配置”面板，通过对话成员查看运行环境并进入成员执行配置。私聊顶部保留该成员模型／推理快捷入口，操作前说明用于此成员之后的私聊和群聊；Runtime 更换进入成员执行配置页。此次不采用上一条建议中的私聊会话覆盖，避免同一成员同时存在两套不易辨认的配置范围。

新请求停止读取会话覆盖；旧覆盖表保留核对，旧写入接口返回 410，旧页面发起新会话覆盖请求要求刷新。已接受请求、历史和已排队工作的冻结快照继续保留；定时安排持有自己的配置。编译及实际使用结果以 [第 7 段](stage-7.md) 和 [当日验收](chat-acceptance-2026-11-15.md) 最新补充为准。

人工交接同样使用接手成员的默认配置；未配置时要求先完成成员设置，不退回上一位的 Runtime。已接受的交接请求继续使用提交时快照。
