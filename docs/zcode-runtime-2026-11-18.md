# ZCode Runtime 接入（2026-11-18）

现在可在成员设置中选择本机 ZCode，通过已登录的智谱 GLM Coding Plan 执行私聊工作。成员的 Runtime 和模型配置仍用于之后的私聊、群聊与定时工作；原运行和历史快照不迁移。本次新增“ZCode 助手”用于真实验收，原有成员和股票安排未切换。新成员已显式选择 Coding Plan 渠道的 GLM-5.3，推理和权限跟随本 Runtime 当前值。

## 实现

调用链为 Hutian 静态 Web → Hutian API → 原 Matrix 独立宿主 → 原 Dock 应用身份/Server → Mac 设备后台 → ACPX → `zcode-acp-server@0.88.0` → 已安装 ZCode app-server。没有在 Web 放模型密钥，也没有把 Coding Plan 换成普通按量 API。

Dock 新增 ZCode 安装发现、模型/推理档位、原生审批和单会话权限配置。后台、CLI 与面板纳入第三个 Harness。dsh 与 ZCode 共用 ACP 会话生命周期、MCP 绑定、事件归并和持久回执，原生环境准备保持各自独立。

模型能力复核：补齐逐模型推理档位，GLM-5.3 与 GLM-5.3-Flash 均从本机 ZCode 原生模型声明读取 `low / high / max`。旧安装版本不支持上游已核验的 deferred-session 探测，因此使用随应用附带的账户模型规则只读投影，保留版本校验；不通过切换真实会话探测。Flash + low 已实际完成 `FLASH_EFFORT_OK`。服务档位仍显示“未报告”：当前接口没有该执行选项，它与购买的 Coding Plan 套餐等级无关。

该能力修复已通过 `pnpm check`（191 passed / 7 skipped）和独立原生调用。首次复核时因活跃工作未重载；随后在处理旧运行待核对问题时确认设备空闲，通过受管停止/启动重载后台，保持原身份和记录。本轮源码按用户授权整理提交并推送；未发布 App/SDK。

社区 bridge 的默认全自动权限不适合直接继承。Dock 创建的 ZCode 会话采用 build（变更前确认），成员可以显式选择它报告的其他原生模式；这是本次会话设置，不重写桌面客户端的全局模型或权限。bridge 配置放在 Dock 私有运行目录，关闭远程服务、额度恢复后自动重试、额外完成提示；不运行依赖包的安装后 Hub 通知脚本。

ZCode ACP 没有 Codex 的 final_answer phase。仅在收到正常 end_turn、且最后内容是助手文本时，将最后一条消息标为最终回答，前序文本仍是过程。失败、取消、工具结尾或缺少终态不提升过程为成果。仍报告 exactFinalAnswer=false，不声称具备 Codex 原生结构化最终消息保证。这补齐了 Matrix 正式发送、过程收起和最终链接对应文件回流。

## 真实验收

- 本机 ZCode CLI 0.17.1；bridge 返回 BigModel Individual Coding Plan，模型为 GLM-5.3，并产生原生模型用量回执。这验证了实际调用渠道，不等于独立审计账单扣减。
- 独立后台路径实测 SDK → Server → Daemon → ZCode：MCP 单次调用、两轮上下文续接、重复请求读取原结果、冲突请求拒绝、断线重连读取原回执通过。
- Hutian 浏览器完成成员创建、绑定 ZCode、读取 GLM-5.3/最高推理、发送消息、原生审批、search_context 和 list_knowledge 回调。
- 第一轮发现“执行完成但缺少最终消息 phase”导致正式发送受阻；原记录保留。修正后新一轮最终回答正式进入 Matrix，过程收起，文件成为附件。
- 浏览器下载附件返回 HTTP 200，内容准确为 ZCODE_HUTIAN_OK；刷新后消息和下载入口仍在。
- 真实原生写入审批等待时取消：返回 cancelled，待写文件不存在，没有把过程文本当最终成果。
- pnpm check 通过：198 项既有检查，191 通过、7 跳过；类型、构建、原面板检查及 GPUI cargo check 通过。只更新三个既有 Harness 列表预期，没有新增测试工程。

私有原始证据位于 `harness-dock/.local/zcode-acceptance/`、`harness-dock/.local/zcode-daemon-acceptance-*/`、`hutian-world/.local/zcode-acceptance/`，不提交凭据、原始会话和本机身份。

## 当前边界

- 社区 ACP 适配，官方接口兼容承诺尚未确认；固定版本使用，升级须重复真实验收。来源：[bridge](https://github.com/william0wang/zcode-acp)、[官方反馈 #286](https://github.com/zai-org/feedback/issues/286)。
- 本轮实测为 Mac。Windows 未安装、配对、修改或实测 ZCode；不宣称双端交付。
- 不支持 Dock 注入额外 Skills；保留 ZCode 自己的原生资产。运行中 steering 未开放：上游在竞争窗口可能转为新一轮，不能据此承诺只补充当前运行。停止已经实测。
- 缺少原生结果查询时，设备故障后的未知结果保持未知，不自动重派发。会话续接经过实测，不承诺任意进程故障继续执行。
- 群聊、定时任务复用成员执行路径，但本轮没有新增真实群聊/定时触发验收，不把代码路径复用写成已实测。
- 当前仅本机开发运行环境加载源码适配；没有制作、发布或安装新的分发 App。本轮源码按用户授权整理提交并推送；未发布 App/SDK。

X 草稿（未发布）：给 Hutian 接上了 ZCode Runtime，终于能用上之前开的 GLM Coding Plan。成员选好 ZCode 后，聊天、工具审批和文件交付都走原来的工作流。这次也踩到了一个实际问题：模型回答完不等于产品交付成功，还得把最终消息和附件接好。现在 Mac 上这条链路实测跑通了。

## 旧运行待核对修复

用户反馈 11:35、11:56 两条工作持续“待核对”，图片请求排队。核对原设备回执确认两条均正常 `end_turn`，但缺少最终文本阶段。11:35 是早期适配生成的旧记录；11:56 还暴露出一个边界：ZCode 在最终回答后重复上报已失败工具的同状态终态，使原先的“最后内容是工具”判断错误地抑制了最终回答。此前工作中的长时间审批流程占用串行入口，后续图片请求在 13:30 开始、约 51 秒执行完成，正式回复在 13:31 已确认。

Adapter 现在只忽略同一工具、相同已终结状态的重复更新对“最后内容”的影响，仍原样发出工具事件；新工具、首次终态、状态变化和非终态更新继续阻止把前面的过程文本当最终回答。正常 end_turn 和最后助手正文条件保持。

两条历史没有改写原设备回执或直接修改业务数据库。设备空闲时只读提取完整原事件，逐字拼接核对最终消息，并按照修正后的规则检查事件顺序，留下私有证据摘要后恢复宿主派生的 `reply.json`。原协调器沿原 Matrix 事务 ID 补送并同步为 replied；网易云的最终回答保留操作受阻、未打开具体歌单的真实说明。原成果接口补取验收文件一份，网易云工作确认无成果文件；没有重放模型、工具或审批。

真实浏览器确认两条最终回答、图片回答均可读，当前工作为零，所有六条 ZCode 历史为 replied，“等待执行”和“成果文件待核对”均消失；Flash 行已报告“低 / 高 / 最高”。原记录重放覆盖 95 / 366 条事件，新增动作、未确认工具结束、终态变化等反例未误判；仅使用忽略目录中的诊断脚本，未新增永久测试。Dock `pnpm check` 通过（198 项：191 通过、7 跳过），面板检查通过，修正后在空闲状态重载后台。证据位于 Dock `.local/zcode-acceptance/stuck-recovery/`、宿主对应原运行目录及 Web `.local/zcode-acceptance/stuck-browser.json`。本轮源码按用户授权整理提交并推送；未发布 App/SDK。
